1. 작업 하나마다 커밋 하나. 커밋 전에 `cargo clippy --workspace --all-targets -- -D warnings` 경고 0, `cargo test --workspace` 통과.

3. 사용자는 PR 없이 `main`에 바로 병합하는 쪽을 원한다. 다만 병합과 푸시는 사용자에게 확인을 받고 한다.
4. Windows 전용 코드는 이 Mac에서 실행할 수 없다. CI로 컴파일과 테스트를 확인하고, 실기기 동작은 사용자에게 시험을 부탁한다.
5. 사용자의 실행 중인 Aun과 `~/Library/Application Support/Aun`의 페어링 정보는 사용자 동의 없이 건드리지 않는다. 테스트는 임시 폴더와 `port: 0`, `discovery: false`로 한다.

### 1. 실기기 점검 (완료, `docs/device-check.md`)

야간 배치에서 실기기로 확인하지 못한 항목이다. 사용자가 시험하고, 문제가 나오면 로그로 원인을 재현한 뒤 고친다. 문제가 나온 항목부터 고친다.

| 항목 | 시험 방법 | 기대 결과 |
|---|---|---|
| 비밀번호 클립보드 제외 | 쓰는 비밀번호 관리자에서 비밀번호 복사 | 상대 기기 클립보드가 바뀌지 않는다. 일반 텍스트는 여전히 간다 |
| 전송 취소 | 큰 파일을 보내는 중에 받는 쪽에서 "취소", 보내는 쪽에서도 한 번 | 받은 폴더에 `.part`와 완성 파일이 없다. 링크가 유지되고 다음 파일이 간다 |
| 여러 파일 전송 | 파일 20~30개를 한꺼번에 끌어다 놓기 | 진행률이 한 줄씩 표시되고 모두 도착한다 |
| 받은 파일 보기 | 받은 줄의 "Finder에서 보기"/"탐색기에서 보기" | 파일이 선택된 채로 폴더가 열린다 |
| 저장 폴더 | "폴더 변경"으로 바탕화면을 고르고 받기, 앱 재시작 | 바탕화면에 저장되고 재시작 후에도 유지된다 |
| Windows 트레이 | 알림 영역 아이콘의 메뉴(열기, 클립보드 공유, 종료) | 각 항목이 동작한다 |
| 로그인 시 자동 실행 | 켜고 로그아웃/로그인(Mac, Windows 각각) | 로그인 후 Aun이 떠 있다 |
| Mac 메뉴 막대 메뉴 | 상태 아이템 메뉴 항목 클릭 | 각 항목이 동작한다(야간 배치는 표시만 확인) |
| 절전 해제 재연결 | Mac 잠자기 1분 → 깨우기. Windows 노트북도 같은 방법 | 로그 `woke after N s asleep: closing links` 뒤 수 초 안에 `link ... up` |
| 주소로 페어링 | IP 직접 입력으로 페어링(가능하면 Tailscale 100.x) | 탐색 없이 연결되고 재시작 후 재연결된다 |

완료 기준: 표의 항목마다 결과(통과/실패/미시험)를 `docs/device-check.md`에 남기고, 실패 항목은 고쳐서 같은 시험으로 다시 확인한다.

### 2. 유휴 상태 깨어남 줄이기 (완료)

야간 측정에서 앱 전체가 창을 열었을 때 초당 약 110번, 창을 닫은 백그라운드에서 초당 약 43번 깨어났다. 이 중 Aun 코드(클립보드 폴링 약 5/s, `aun-keep` 0.2/s, 링크 핑 0.1/s)는 일부이고 나머지는 메인 스레드(rune/AppKit) 쪽이다(`docs/overnight-report.md` G).

- 어디서 깨어나는지 찾는다. 예: Instruments의 System Trace 또는 `dtrace`/`powermetrics`로 스레드별 wakeup 원인, rune의 프레임 스케줄링과 `poll` 훅, `release_gpu_when_closed` 이후의 이벤트 루프 타이머.
- rune 설정으로 줄일 수 있으면 그렇게 하고, rune을 고쳐야 하면 패치 범위와 근거를 정리해 사용자에게 먼저 묻는다.
- 완료 기준: 바꾸기 전후 깨어남 횟수(창 열림/닫힘), 유휴 CPU, 메모리를 표로 남긴다. 줄지 않으면 바꾸지 않는다. Windows는 가능하면 사용자에게 작업 관리자 수치를 부탁한다.

#### 결과 (2026-11-21)

**위의 110/s, 43/s는 잘못 읽은 값이었다.** `top`의 CSW 열은 누적값이고, 야간 측정은 실행 직후 시작 구간의 누적을 시간으로 나눈 값이었다. 실행 후 40 s가 지나 안정된 뒤 10 s 구간 증가량으로 재면 훨씬 낮다.

측정 방법: Mac mini M4 Pro, release 빌드 사본, `HOME=<스크래치>`. 실행 40 s 뒤 `top -l 7 -s 10 -pid <pid> -stats pid,cpu,csw,idlew`의 2~6번째 구간 증가량 평균(첫 구간은 창 표시 등의 일시적 폭증이 섞여 뺐다). 메모리는 `footprint`의 phys_footprint. xctrace를 붙이면 CSW가 크게 부풀어서(10 s에 1만 회 이상) 트레이스와 수치 측정은 따로 돌렸다. 스크래치 인스턴스는 링크가 없다. 처음 두 번의 실행 뒤 사용자의 Aun이 내려가(원인 미확인) 이후 측정에서는 스크래치 인스턴스가 47810/47811을 잡았고, 탐색이 켜졌으며, 사용자의 Windows PC가 5 s마다 47810에 접속해 거절당했다. 아래 컨텍스트 전환 표는 전후 모두 이 조건(탐색 켜짐, 거절되는 접속 있음)에서 쟀다. **다음부터 앱 단위 측정은 `port: 0`, `discovery: false`로 고친 버리는 빌드로 해야 한다**(작업 규칙 5).

- 바꾼 것: 클립보드 공유가 꺼져 있거나 연결된 기기가 없으면 `aun-clip`이 폴링을 멈추고 채널에서 잠든다. 링크가 올라오거나 공유를 켜면 노드가 깨운다. 잠든 동안의 복사는 이전처럼 보내지 않는다. 공유를 끈 동안 클립보드 텍스트를 읽던 것도 없어졌다.

- 남은 깨어남 중 Aun 몫은 연결된 상태의 클립보드 폴링(초당 약 6번)과 탐색(초당 약 5번)이 비슷하고, 나머지는 macOS 메뉴 막대와 AppKit 쪽이다.

Windows에서 위와 같은 방법(`port: 0`, 탐색 켜짐, `--background`)으로 잰 `aun-discovery`는 3.12 → 2.86/s, 프로세스 전체는 3.4 → 3.1/s였다. 줄어든 폭이 작은 것은 1 s 안에 패킷이 거의 늘 오기 때문이다: 이 PC는 3 s마다 `255.255.255.255`와 `192.168.0.255`로 방송해 메아리 2개를 받고, 같은 LAN의 Mac Aun 방송도 받는다. 시한 만료로 깨어나는 것만 줄어드므로 다른 Aun이 없는 조용한 네트워크에서 효과가 더 크다(최대 약 0.3/s). Mac에서는 재지 않았다.
- 연결된 상태의 폴링을 더 줄이려면 macOS에는 변경 알림이 없어 간격을 늘리는 수밖에 없다(복사 후 전달 지연과 맞바꿈).

Windows(2026-11-21): Windows 11 Pro PC, release 빌드. 변경 전 `42967de`와 변경 후 `c24ee7e`에 같은 측정용 패치(`port: 0`, `discovery: false`, `single_instance` 이름 변경, 자동 실행 갱신 생략)를 적용해 임시 폴더에 빌드하고, `APPDATA`를 임시 폴더로 바꿔 실행했다. 링크와 탐색, 외부 접속이 없다. Mac과 같은 방법으로 실행 40 s 뒤 10 s 간격 표본 7개를 받아 2~6번째 구간 증가량을 평균했다. 컨텍스트 전환은 `Win32_PerfRawData_PerfProc_Thread`의 스레드별 누적값(`ContextSwitchesPersec`)을 합한 값이고, 구간 사이에 끝난 스레드는 빠진다. 메모리는 작업 관리자의 메모리 열과 같은 private working set이고, 괄호 안은 커밋(`PrivateMemorySize64`)이다. IDLEW에 해당하는 값은 없다. 창 닫기는 제목 표시줄 X와 같은 `WM_SYSCOMMAND`/`SC_CLOSE`로 했고, 닫은 뒤에도 프로세스가 살아 있었다.

| 상태 | 컨텍스트 전환/s (전 → 후) | `aun-clip`/s (전 → 후) | 유휴 CPU | private WS (커밋) |
|---|---|---|---|---|
| `--background` | 4.4 → **0.2** | 4.24 → 0 | 0.00% | 3.2 MB (4.0–4.2 MB) |
| 창 열림 | 4.7 → **0.2** | 4.47 → 0 | 0.00% | 28–33 MB (57–62 MB) |
| 창을 연 뒤 닫음 | 4.6 → **0.3** | 4.38 → 0 | 0.00–0.02% | 22 MB (51 MB) |

- 변경 후 남은 깨어남은 `aun-keep`의 5 s 점검(0.2/s)이 거의 전부다. 메인 스레드, `rune-tray`, D3D 스레드는 세 상태 모두 0.00–0.01/s였다. Mac의 메뉴 막대 쪽 깨어남에 해당하는 것은 Windows에 없다.
- 변경 전 창 열림 첫 측정에서 한 구간만 메인 스레드가 133/s로 튀었다(창 다시 그리기 등 일시적 사건으로 보인다). 같은 조건을 다시 재서 튐이 없는 값을 표에 적었다.
- 메모리는 창을 닫으면 약 33 → 22 MB로 줄지만 창을 연 적 없는 3.2 MB까지는 돌아가지 않는다(Mac과 같은 양상).
- 연결된 기기가 있을 때는 상대 기기가 없어 재지 않았다(폴링이 유지되므로 변경 전과 같을 것으로 본다).

### 3. 작은 개선

- ~~이미지가 텍스트에 밀리는 경우~~ (재현되지 않음): 이미지를 복사할 때 클립보드에 텍스트(파일 이름이나 URL)도 함께 들어가면 지금 코드(`clip.rs`의 `run`)는 텍스트만 보낸다. 브라우저의 "이미지 복사" 등에서 실제로 그런지 먼저 재현하고, 그렇다면 이미지 형식이 있을 때 이미지를 우선하도록 고친다. 다만 Excel·Numbers의 셀 복사도 텍스트와 그림을 함께 넣으므로 무조건 이미지를 우선하면 안 된다.
  - Mac Chrome "이미지 복사"(2026-11-21): `public.png`, `public.tiff`, `public.html`, `org.chromium.source-url`이 들어가고 일반 텍스트는 없다. arboard `get_text`는 `ContentNotAvailable`, `get_image`는 1920x1560을 돌려주므로 이미지가 간다. **이 경우는 밀리지 않는다.**
  - Mac Safari "이미지 복사"(2026-11-21): `public.tiff`, `com.apple.flat-rtfd`, `com.apple.webarchive`, `public.html`이 들어가고 일반 텍스트는 없다. `get_text`는 `ContentNotAvailable`, `get_image`는 1500x1026. **역시 밀리지 않는다.** Mac에서는 고칠 것이 없다.
  - Windows 브라우저 "이미지 복사"(2026-11-21, 사용자 실기기 확인): 이미지가 Mac으로 간다. 브라우저 종류와 클립보드 형식은 기록하지 않았다. **고칠 것이 없어 이 항목을 닫는다.**
- ~~연결된 기기가 없을 때 클립보드 폴링 간격 늘리기~~: 2번에서 공유가 꺼졌거나 연결이 없으면 폴링을 아예 멈추도록 했다.
- ~~파일을 복사하면 상대 기기로 파일 전송~~ (2026-11-21, 사용자 결정: 앱에서 확인 후 보내기, 파일만):
  - 클립보드에 파일 참조(`public.file-url`, `CF_HDROP`)가 있으면 `clip.rs`가 텍스트 대신 파일 목록을 노드에 알리고(`Note::Copied`), 창에 "복사한 파일 N개" 안내와 연결된 기기마다 "‹기기›로 보내기" 버튼을 띄운다. 메뉴 막대/트레이에는 "복사한 파일 보내기" 항목이 나타나고, 연결된 기기가 하나면 바로 보내고 아니면 창을 연다.
  - 폴더는 보내지 않고 안내에 "폴더 N개는 보낼 수 없어요"를 붙인다. 폴더만 복사하면 안내를 띄우지 않는다.
  - 바뀐 동작: Mac에서 Finder로 파일을 복사해도 이제 파일 이름 텍스트는 상대 클립보드로 가지 않는다.
  - 한계: 클립보드 감시가 도는 동안(클립보드 공유 켜짐, 연결된 기기 있음)만 알아챈다. 파일 참조와 이미지를 함께 넣는 앱에서는 이미지 동기화 대신 파일 안내가 뜬다.
  - 실기기 시험 통과(2026-11-21, CI 44894404006 빌드, Mac ↔ Windows): Finder ⌘C, 탐색기 Ctrl+C로 파일 1개, 여러 개, 폴더 섞어 복사 → 창 안내와 보내기, 폴더 제외 안내, 창을 닫은 상태의 메뉴 막대/트레이 항목, 파일 이름 텍스트가 상대 클립보드로 가지 않음.
- ~~끊긴 지점부터 이어 보내기(재개)~~ (2026-11-21):
  - 받는 쪽은 연결이 끊기거나 보내는 쪽이 취소하면 `.part`를 남긴다. 받는 쪽이 직접 취소하거나, 보내는 쪽이 파일을 읽지 못했거나, 쓰기에 실패하면 지운다.
  - 보내는 쪽은 이번 실행 중에 중간에 멈춘 파일을 같은 기기로 다시 보낼 때만(다시 보내기, 다시 끌어다 놓기) `FileStart`에 `resume`을 켜고, 받는 쪽의 `FileFrom { offset }`을 기다린 뒤 거기서부터 보낸다. 처음 보내는 파일은 기다리지 않는다.
  - 같은 파일인지는 보내는 쪽 기기, 파일 이름, 크기, 수정 시각(ns)으로 판단한다. 다르면 받는 쪽은 낡은 `.part`를 지우고 0부터 받는다. 내용 해시는 비교하지 않는다.
  - 통신 형식: `Hello`와 `FileStart` 끝에 바이트를 덧붙였고(옛 빌드는 이름 뒤를 읽지 않는다), 새 프레임 `FileFrom`(종류 11)은 `Hello`로 지원을 알린 상대에게만 보낸다. 옛 빌드와 섞이면 지금처럼 처음부터 보낸다.
  - 한계: 남긴 `.part` 목록은 메모리에만 있어서 앱을 다시 시작하면 이어 보내지 못하고, 그 `.part`는 받은 폴더에 남는다. 저장 폴더를 바꾼 뒤, 또는 그 사이에 받은 폴더에 같은 이름의 파일이 생긴 경우에도 처음부터 보내고, 새 파일은 `이름 (1).확장자`로 받는다(기존 파일을 덮어쓰지 않는다).
  - 실기기 시험 통과(2026-11-21, CI 44891270710 빌드, `docs/device-check.md`). 시험 방법: Mac ↔ Windows로 큰 파일을 보내다가 (1) 보내는 쪽에서 취소, (2) 보내는 쪽을 잠자기로 끊고, 각각 "다시 보내기"를 눌러 로그에 `sending <파일> from <N> of <M> bytes`가 찍히고 받은 파일이 원본과 같은지(크기, 가능하면 해시) 본다.
- ~~강조한 행으로 자동 스크롤~~: 중복 전송 때 강조하는 행을 기록 목록 안에서 보이도록 스크롤한다(rune `Tx::scroll_into_view_in`).
- ~~점검에서 남은 한계: 깨어남 알림을 놓쳤을 때의 안전장치~~: 입력 기반 안전장치를 넣었다(`docs/device-check.md` 알려진 한계).
- 점검에서 남은 한계: 메뉴 막대 비밀번호 관리자 판별. 이 Mac에 설치된 비밀번호 관리자는 Apple 암호 앱뿐이고(창, 메뉴 막대 모두 통과), Chrome 비밀번호 관리자는 비밀 표시를 넣는다. 재현할 대상이 없어 코드는 바꾸지 않았다. 다른 관리자(1Password, Bitwarden 등)를 쓰게 되면 그 앱으로 재현한 뒤 고친다.

### 4. 배포 형태 (완료)

사용자 결정(2026-11-21): Mac은 ad-hoc 서명한 `.app`을 zip으로, Windows는 단일 exe. 아이콘은 트레이 아이콘 도안(`scripts/icon.swift` → `assets/`).

- Mac: `scripts/bundle-mac.sh`. `LSUIElement`는 넣지 않았다(앱이 "Dock 아이콘" 설정으로 직접 정한다). 번들 앱은 macOS 15부터 LAN 접근에 `NSLocalNetworkUsageDescription`가 필요해 넣었다. arm64만 만든다. 공증은 Developer ID가 없어 하지 않는다.
- Windows: `app/build.rs`(winresource)로 아이콘과 버전 정보를, `.cargo/config.toml`로 정적 C 런타임을 넣었다. CI가 버전 정보와 `VCRUNTIME140` 미포함을 확인한다.
- Mac 실기기(2026-11-21, CI 44905805181의 `Aun-mac.zip`을 `gh run download`로 받아 `/Applications`에 풀기): 아이콘 표시 확인(사용자). 로그상 Windows PC와 LAN(`192.168.0.15`)으로 링크가 올라간 뒤 Tailscale 링크로 바뀌었고, LaunchAgent는 `/Applications/Aun.app/Contents/MacOS/aun`을 가리킨다. `gh`로 받은 파일에는 quarantine 속성이 없어 Gatekeeper 경고는 시험되지 않았다. 로컬 네트워크 허용 창이 떴는지는 기록하지 않았다.
- Windows 실기기(2026-11-21, 같은 실행의 `aun.exe`): 탐색기 아이콘과 속성 > 자세히의 제품 이름·버전 확인(사용자). 예전 exe를 끄고 새 exe를 실행하자 Mac 로그에서 옛 링크가 `ConnectionReset`으로 내려가고 3.8 s 뒤 LAN(`192.168.0.15:47810`)으로 새 링크가 올라왔다.
- 첫 실행 경고(사용자 확인): Mac Gatekeeper 경고와 Windows SmartScreen 경고가 모두 떴다. 서명이 없어 예상한 동작이며, 각각 우클릭 > 열기, 추가 정보 > 실행으로 넘어간다. 실기기 확인을 마쳤다.

이전 계획:

- Mac: `.app` 번들(아이콘, `Info.plist`, `LSUIElement` 검토), 서명과 공증 여부. 서명이 없으면 Gatekeeper 경고가 뜬다.
- Windows: 아이콘과 버전 정보가 들어간 exe, 설치 방식(설치 파일 또는 단일 exe).
- CI에서 두 산출물을 아티팩트로 만든다.

### 5. 마우스·키보드 공유(KVM) 구현 (사용자가 지켜보는 상태에서만)

설계는 `docs/kvm-design.md`에 있다. 입력을 가로채는 기능이므로 무인으로 진행하지 않는다. 단계마다 실기기에서 사용자와 함께 확인하고, 실패하면 입력을 되돌려 주는 안전장치를 먼저 만든다.

- 1단계(받는 쪽 주입) 중 마우스 부분을 구현했다(2026-11-21, `docs/kvm-design.md` 8절). 입력을 가로채지 않는다.
- 실기기 시험 방법: 받는 기기에서 "원격 조작 허용"을 켜고(Mac은 시스템 설정 > 개인정보 보호 및 보안에서 허용. macOS 27은 "System & App Protection Override"에 있고 "손쉬운 사용" 목록에는 나오지 않는다. 2026-11-22 확인), 보내는 기기에서 그 기기 줄의 "원격 조작"을 눌러 나온 패드 위에서 움직이기, 클릭, 더블클릭, 끌기, 오른쪽 클릭, 스크롤. 끌기 도중 "그만"을 누르거나 보내는 쪽을 잠자기로 끊으면 받는 쪽 버튼이 떼어져야 한다. 방향(특히 스크롤)과 속도를 기록한다.
- 실기기 시험 통과(2026-11-22, Mac은 CI 44912189217의 `Aun-mac.zip`, Windows는 같은 실행의 `aun.exe`): 양방향(Mac ↔ Windows)으로 움직이기, 클릭, 더블클릭, 오른쪽 클릭, 스크롤, Finder·탐색기 끌기, 끌기 도중 "그만"을 누르면 받는 쪽 버튼이 떼어짐. 사용자 확인. Mac 로그 `input from KIBEOMKWON (injection allowed by the OS: true)`.
  - macOS 27에서는 입력을 주입하는 앱을 "손쉬운 사용"이 아니라 개인정보 보호 및 보안 > "System & App Protection Override"에서 허용한다. Aun이 목록에 자동으로 나타나지 않아 사용자가 +로 추가했다(원인 미확인). 추가한 뒤 Aun을 다시 시작하지 않아도 적용됐다.
  - 시험 뒤 고친 것: 좁은 창에서 기기 줄 버튼이 잘리던 것과 권한 안내 문구(`cc3c70c`, 실기기 미확인).
- 1단계 키 입력을 구현했다(2026-11-22, `docs/kvm-design.md` 8절 "키 입력"). 실기기 시험 항목: 글자·숫자·기호, Shift 조합, 화살표·Backspace·Enter·Tab(Tab이 Aun 안에서 포커스를 옮기지 않고 상대로 가는지), 키 반복, 오른쪽 Alt/Option·오른쪽 Ctrl/⌘·한/영(양방향, 결과를 3단계 자료로 기록), 키를 누른 채 다른 창 클릭하기와 "그만" 누르기(받는 쪽 키가 떼어지는지), Mac 보내는 쪽에서 ⌘Q.
- 키 입력 실기기 시험(2026-11-22, CI 44971190007 빌드 `d3d1f90`, 사용자 확인):
  - 양방향으로 문자·숫자 키가 들어간다.
  - Windows → Mac에서 처음에는 Backspace와 Enter만 들어가지 않았다. 원인은 새 빌드가 macOS 권한을 잃은 것이었다(Mac 로그 `injection allowed by the OS: false`). System & App Protection Override에서 Aun을 지웠다가 다시 추가하자 들어갔다. 권한이 없을 때 macOS 27은 주입한 일반 문자는 통과시키고 Return·Delete 같은 제어 키는 막는 것으로 보인다(관찰한 것은 이 두 키뿐).
  - 같은 주입 코드로 TextEdit에 A·B·Backspace·Return·C를 넣는 시험(권한 있는 프로세스)에서 Backspace와 Return이 동작했다. 보내는 쪽 Mac 패드도 Backspace·Enter를 받는 것을 디버그 빌드로 확인했다.
  - 예상한 한계: 수정 키(Ctrl/Alt ↔ ⌘/Option)는 물리 위치대로 가고, Mac 받는 쪽은 한/영을 버린다(3단계).
  - 추가 시험(2026-11-22, 사용자 확인): Tab은 받는 쪽에 들어가고 보내는 쪽 Aun의 포커스를 옮기지 않는다. 키 반복이 되고 떼면 멈춘다. Shift를 누른 채 다른 버튼이나 "그만"을 누르면 받는 쪽 Shift가 떼어진다.
  - Mac 보내는 쪽 ⌘Q: 키가 상대에게 가고(Windows에서 Win+Q로 검색 창이 열림) 동시에 AppKit 메뉴가 Mac Aun을 종료한다. 링크가 끊기며 Windows의 Win 키는 떼어졌다. 한 키가 두 곳에서 처리되는 문제로 남겨 둔다(Quit 메뉴 단축키를 바꿀지는 사용자 결정, 3단계의 수정 키 맞바꾸기와 함께 정한다).
  - 남은 문제: ad-hoc 서명이라 새 빌드마다 macOS 권한을 다시 추가해야 한다. 서명 인증서를 고정하면 유지될 가능성이 있다(미확인).
  - 원인 확인(2026-11-22): CI 44971190007과 44912189217의 `Aun.app`에 `codesign -d -r-`를 하면 둘 다 `designated => cdhash H"..."`이고 해시가 다르다. ad-hoc 서명은 지정 요구사항(designated requirement)이 cdhash뿐이라 빌드마다 다른 앱이 된다.
  - 조치: `bundle-mac.sh`가 `MAC_SIGN_IDENTITY`가 있으면 그 인증서로 서명하고, 없으면 ad-hoc으로 서명한다. CI는 `MAC_SIGN_P12`(base64 .p12)와 `MAC_SIGN_P12_PASSWORD` 시크릿이 있으면 임시 키체인에 넣고 그 인증서로 서명한다. 임시 자체 서명 인증서로 서로 다른 두 빌드를 서명하면 둘 다 `identifier "dev.aun.desk" and certificate leaf = H"<같은 값>"`이 됐다. 인증서와 시크릿은 사용자가 만든다. 인증서로 서명한 첫 빌드는 권한을 한 번 더 지웠다 추가해야 한다(요구사항 형태가 바뀜). 그 뒤 두 빌드를 연달아 설치해도 권한이 유지되는지는 실기기 미확인.
- 3단계 키 매핑을 구현했다(2026-11-22, `docs/kvm-design.md` 4절과 8절 3번). 사용자 결정: 수정 키 맞바꾸기는 보내는 쪽 설정(기본 켬), ⌘ 단축키는 패드에서 ⌘를 누른 동안 메뉴를 떼기, 한/영은 받는 쪽과 보내는 쪽 모두, 미디어 키는 미룸.
