# 마우스·키보드 공유(KVM) 설계

작성: 2026-11-21 야간 배치. 구현하지 않은 설계다. 입력을 가로채는 코드는 실기기에서 단계마다 확인하면서 넣는다.

목표: Mac과 Windows PC를 나란히 놓고, 한쪽의 마우스와 키보드로 화면 가장자리를 넘어 다른 쪽을 조작한다. 기존 링크(Noise XX, TCP 47810)와 페어링을 그대로 쓴다. TwinDesk의 `docs/protocol.md`(tdv1/tdv2)와 `docs/full-kvm.md`에서 개념(누적 이동량, 번호 붙인 이벤트, 별도 UDP 경로)만 참고했고 코드는 가져오지 않는다(GPL-3.0).

## 용어

- **주는 쪽(driver)**: 사용자가 실제로 만지는 마우스·키보드가 달린 기기. 입력을 가로채 보낸다.
- **받는 쪽(driven)**: 입력을 주입받는 기기.
- **건너감(crossing)**: 포인터가 경계를 넘어 다른 기기로 넘어간 상태. 건너갈 때마다 번호(`route`)가 바뀐다.

## 1. 화면 배치와 가장자리 판정

- 배치는 기기마다 하나의 "이웃 방향"으로 시작한다: 상대가 이 기기의 왼쪽/오른쪽/위/아래 중 어디에 있는지. 설정에 저장하고 상대에게도 반대 방향으로 알린다(`KvmLayout` 프레임). 여러 모니터 배치(겹친 좌표계)는 2단계.
- 화면 목록: macOS `CGGetActiveDisplayList` + `CGDisplayBounds`(전역 좌표, 주 화면 원점), Windows `EnumDisplayMonitors` + `GetMonitorInfoW`(가상 화면 좌표). 해상도·배치가 바뀌면(`CGDisplayRegisterReconfigurationCallback`, `WM_DISPLAYCHANGE`) 다시 읽는다.
- 가장자리 판정은 모든 화면의 합집합 경계에서 한다. 이웃 방향 쪽 바깥 경계에 포인터가 닿고, 그 방향으로 계속 밀 때(누적 2 px 이상) 건너간다. 화면 사이의 안쪽 경계는 건너감이 아니다.
- 실수 방지(선택): 가장자리에 250 ms 머물러야 건너가기, 또는 수정 키를 누른 채일 때만 건너가기. 기본은 즉시.
- 들어가는 위치: 나간 지점의 상대 높이(0~1)를 받는 쪽 화면 높이에 비례해 옮긴다(왼쪽/오른쪽 이웃일 때). 받는 쪽 반대 가장자리 1 px 안쪽에서 시작한다.
- 돌아오기: 받는 쪽은 주입한 포인터가 돌아오는 방향 가장자리에 닿으면 주는 쪽에 `KvmReturn`을 보낸다. 주는 쪽이 판정하지 않는 이유는 받는 쪽의 화면 배치를 주는 쪽이 정확히 알 수 없기 때문이다.

## 2. macOS

### 캡처(주는 쪽)

- `CGEventTapCreate(kCGSessionEventTap, kCGHeadInsertEventTap, kCGEventTapOptionDefault, mask, …)`. 마스크: 마우스 이동/드래그, 버튼 down/up, 스크롤, 키 down/up, `flagsChanged`.
- 건너간 동안에만 이벤트를 삼킨다(콜백이 NULL 반환). 평소에는 이동 이벤트만 보고 그대로 통과시킨다(가장자리 판정용). 건너가 있지 않을 때 키 이벤트는 탭 마스크에서 뺀다. 타이핑 지연을 만들 이유가 없다.
- 건너간 동안 포인터는 화면 가장자리에 고정한다: `CGAssociateMouseAndMouseCursorPosition(false)`로 커서를 떼고 `CGDisplayHideCursor`. 이동량은 이벤트의 `kCGMouseEventDeltaX/Y`로 읽는다(절대 위치는 고정이므로).
- 권한: 접근성(`AXIsProcessTrustedWithOptions`로 확인·요청). 키 입력 감시는 macOS 10.15+에서 "입력 모니터링" 권한도 필요하다(`IOHIDRequestAccess(kIOHIDRequestTypeListenEvent)`). 권한이 없으면 KVM 토글을 끄고 설정 화면으로 안내한다.
- 탭이 꺼지는 경우: 콜백이 늦으면 시스템이 `kCGEventTapDisabledByTimeout`으로 탭을 끈다. 콜백은 큐에 넣기만 하고 즉시 반환해야 하며, 이 이벤트를 받으면 `CGEventTapEnable(tap, true)`로 다시 켠다. 탭 스레드는 자기 `CFRunLoop`를 돌리는 전용 스레드.
- 보안 입력: 비밀번호 칸 등에서 `IsSecureEventInputEnabled()`가 참이면 키 이벤트가 탭에 오지 않는다. 이때 건너가 있으면 주는 쪽으로 강제 복귀하고 상태 줄에 이유를 보인다.

### 주입(받는 쪽)

- `CGEventCreateMouseEvent` / `CGEventCreateKeyboardEvent` / `CGEventCreateScrollWheelEvent2` → `CGEventPost(kCGHIDEventTap, …)`.
- 이동은 절대 위치로 주입하되 `kCGMouseEventDeltaX/Y` 필드도 채운다(게임, 3D 앱은 델타만 읽는다). 버튼을 누른 채 이동은 `kCGEventLeftMouseDragged`.
- 수정 키 상태는 `CGEventSetFlags`로 이벤트마다 붙인다. 따로 누른 수정 키는 `kCGEventFlagsChanged`.
- 더블클릭: `kCGMouseEventClickState`를 직접 센다(주는 쪽 OS의 클릭 횟수를 그대로 전달).
- 권한: 주입에도 접근성 권한이 필요하다.

## 3. Windows

### 캡처(주는 쪽)

- `SetWindowsHookExW(WH_MOUSE_LL)`, `SetWindowsHookExW(WH_KEYBOARD_LL)`, 메시지 루프를 도는 전용 스레드에서. 건너간 동안 훅이 1을 반환해 이벤트를 삼킨다.
- 이동량: 저수준 훅의 `MSLLHOOKSTRUCT.pt`는 가속이 적용된 절대 좌표다. 건너간 동안은 커서를 가장자리에 `SetCursorPos`로 되돌리고 그 차이를 이동량으로 쓴다. 더 정확한 방법은 Raw Input(`RegisterRawInputDevices`, `RIDEV_INPUTSINK`)의 상대 이동량이다. 1단계는 훅, 2단계에서 Raw Input.
- 주입한 이벤트가 다시 훅에 걸리지 않게 `LLMHF_INJECTED` / `LLKHF_INJECTED`를 거른다. 단 다른 프로그램(원격 데스크톱 등)이 주입한 입력은 통과시켜야 하므로, 주입할 때 `dwExtraInfo`에 Aun 표식(상수)을 넣고 그것만 거른다.
- 훅 시간 제한: 콜백이 레지스트리 `LowLevelHooksTimeout`(값은 Windows 버전마다 다르다, 실기기에서 확인)을 넘기면 Windows가 훅을 조용히 뗀다. 콜백은 큐에 넣고 바로 반환한다. 주기적으로(1 s) 훅이 살아 있는지 확인하는 방법은 공식적으로 없으므로, 건너간 동안 이벤트가 2 s 이상 안 오면 훅을 다시 건다.
- 보안 데스크톱(UAC, 잠금 화면, Ctrl+Alt+Del)과 관리자 권한 창: 사용자 권한 프로세스는 입력을 보지도 주입하지도 못한다(UIPI). 1단계 범위 밖. 그 상태를 감지하면(`OpenInputDesktop` 실패 또는 이름이 `Default`가 아님) 강제 복귀한다. TwinDesk는 이것을 서비스(LocalSystem)와 에이전트로 푼다. Aun은 필요해지면 별도 설계.

### 주입(받는 쪽)

- `SendInput`. 이동은 `MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`(0~65535 정규화 좌표), 휠은 `MOUSEEVENTF_WHEEL` / `MOUSEEVENTF_HWHEEL`(120 단위).
- 키는 스캔 코드로 주입한다(`KEYEVENTF_SCANCODE`, 확장 키는 `KEYEVENTF_EXTENDEDKEY`). 가상 키 코드로 주입하면 받는 쪽 키보드 배열에 따라 다른 글자가 나온다.
- `dwExtraInfo` = Aun 표식(위 캡처 참고).

## 4. 키 코드 매핑

- 선(wire)에는 **USB HID 사용 코드**(Keyboard/Keypad page 0x07)를 싣는다. 물리 키 위치 기준이라 배열(한글 2벌식, 영문, 일본어)과 무관하다. 문자를 보내지 않는다. 받는 쪽 OS의 입력기가 글자를 만든다.
- macOS: `kCGKeyboardEventKeycode`(가상 키 코드, ANSI 위치 기준) ↔ HID 표. Windows: 스캔 코드(세트 1, 확장 플래그 포함) ↔ HID 표. 두 표는 코드에 상수 배열로 둔다(약 110개 키). 공개 표(USB HID Usage Tables 1.4, Apple `Events.h`, Microsoft "Keyboard scan codes")에서 만든다.
- 수정 키 대응: 기본은 **물리 위치 그대로** 보낸다(Mac Command는 Windows 키, Option은 Alt, Control은 Ctrl). "Mac 단축키 습관 유지" 옵션을 켜면 Mac에서 Windows로 갈 때 Command와 Control을 맞바꿔 ⌘C가 Ctrl+C가 되게 한다.
  - 구현(3단계, 2026-11-22): 보내는 쪽 설정 `swap`(패드 머리의 "⌘·Ctrl 맞바꾸기", 기본 켬). 켜져 있으면 패드가 HID Control(0xE0/0xE4)과 GUI(0xE3/0xE7)를 왼쪽·오른쪽 각각 맞바꿔 보낸다. 프로토콜은 그대로다(`Hello`에 상대 OS가 없어 받는 쪽에서는 할 수 없다). Mac 패드의 ⌘C는 Windows에서 Ctrl+C, Windows 패드의 Ctrl+C는 Mac에서 ⌘C가 된다. 설정 버튼을 누르면 패드가 포커스를 잃어 눌린 키를 먼저 떼므로, 바꾼 뒤 엉뚱한 키가 눌린 채 남지 않는다.
- 한/영 키, 한자 키: HID `Lang1`(0x90), `Lang2`(0x91). macOS에서는 `kVK_JIS_Kana`/`Eisu`가 아니라 입력 소스 전환이므로, Mac이 받는 쪽일 때 `Lang1`은 입력 소스 전환 단축키(기본 Ctrl+Space 또는 Caps Lock)로 바꿔 주입하는 옵션이 필요하다. 실기기 확인 필수.
  - 구현(3단계, 2026-11-22): Mac 받는 쪽은 `Lang1`을 받으면(눌릴 때 한 번) 시스템 설정의 "이전 입력 소스 선택"(`com.apple.symbolichotkeys` 60), 꺼져 있으면 "다음 입력 소스 선택"(61) 단축키를 그 수정 키 flags와 함께 주입한다. 항목이 없으면 macOS 기본값(⌃Space, ⌃⌥Space)이다. `Lang2`는 한국어 입력기의 한자 변환인 ⌥Return으로 주입한다. 두 키는 누를 때마다 전환하므로 받는 쪽 `Injector`가 반복을 버린다. 주입한 F키 이벤트의 flags를 0으로 덮으면(기본값 `0x20800000`의 보조 Fn 비트가 빠짐) F19 단축키가 동작하지 않아서, 이벤트 기본 flags에 단축키 flags를 더한다. 수정 뒤 실제 코드 경로(`Os::key(0x90)`)로 TextEdit 앞에서 F19를 두 번 주입해 2벌식 → ABC → 2벌식을 확인했다. ⌃Space(macOS 기본값)처럼 수정 키가 있는 단축키는 Control flagsChanged 없이 flags만 붙이므로, 동작하는지 미확인이다.
  - Fn 플래그 고착(2026-11-22 실기기에서 발견, 수정): Windows 패드에서 한/영을 누른 뒤 `f`를 누르자 Mac의 Zed 창이 화면을 채웠다. 주입한 F19에 붙은 보조 Fn 플래그(`0x800000`)가 시스템의 수정 키 상태(`CGEventSourceFlagsState`)에 남아, 그 뒤 만든 모든 키 이벤트가 이를 물려받았기 때문이다(`f`가 Globe+F "채우기"가 됨). TextEdit 앞에서 재현했다: F19 주입 뒤 상태가 `0x20000100`에서 `0x20800000`으로 바뀌고 새 `f` 이벤트의 flags도 `0x20800000`이었다. 1단계부터 있던 문제이기도 하다: 오른쪽 화살표 하나만 주입해도 `0x20a00100`(Fn + 숫자 키패드)이 남았다. 이제 Fn 플래그가 붙은 이벤트를 주입한 뒤에는 `flagsChanged`(`kVK_Function`)로 상태를 받는 쪽이 기억하는 수정 키로 되돌린다. 수정 뒤 실제 코드 경로로 한/영과 화살표를 주입해 상태가 `0x20000100`으로 남는 것을 확인했다. 그러나 실기기에서는 이것으로 부족했다: 진단 로그에 한/영 뒤 첫 키가 0.2~0.7 s 뒤에도 `0x20800000`으로 찍혔다. 되돌리는 이벤트는 바로 반영되지 않고(같은 프로세스에서 게시 직후 상태를 읽으면 그대로다), 실제 앱에서는 그 뒤 다시 고착됐다. 전용 이벤트 소스(`kCGEventSourceStatePrivate`)에서 이벤트를 만드는 방법도 시험했다. 테스트 프로세스에서는 깨끗했지만, 실제 앱에서는 첫 키가 여전히 `0x20800000`이었다(5차 시험, 원인 미확인). 그래서 이제 키 이벤트를 게시하기 직전에 Fn·숫자 키패드 비트를 지우고 그 키 자신의 비트만 다시 붙인다(`mac::own_flags`). 키 자신의 비트는 새 전용 소스로 키 코드 0~0x7F를 모두 만들어 잰 값이다: Fn은 F키와 화살표 주변 키, 키패드 비트는 키패드와 화살표. 같은 프로세스에서 세션 상태를 `0x20a00000`으로 고착시킨 뒤 `Os`로 주입하자 `f`는 `0x20000000`, 오른쪽 화살표는 `0x20a00000`으로 게시됐다.
  - 보내는 쪽은 이 키보드에서 한/영·한자인 키를 `Lang1`/`Lang2`로 보낸다(`kvm::lang_keys`, 패드를 열 때 읽고 로그에 남김). Windows: 한국어 배열이 `VK_HANGUL`/`VK_HANJA`로 바꾸는 키(`MapVirtualKeyExW`). 사용자 노트북(ASUS VivoBook S5602ZA, `KBDKOR.DLL`)의 한자 키는 물리적으로 오른쪽 Ctrl(`E0 1D`)이라, 패드가 그 키를 오른쪽 Ctrl(맞바꾸기가 켜져 있으면 ⌘)로 보내고 있었다. `MapVirtualKeyExW`가 이 배열의 특수 키(`KBDSPECIAL`)에도 `VK_HANJA`를 주는지는 실기기 로그로 확인해야 한다.
  - Mac 보내는 쪽은 키가 아니라 입력 소스 전환 자체를 보낸다. 실제 키보드에서 입력 소스 단축키 키(이 Mac은 `hidutil`로 F18이 된 Caps Lock)는 시스템이 가져가고 앱에는 오지 않는다. 시험 창 앱에서 사용자가 Caps Lock을 두 번, `a`를 한 번 눌렀을 때 `a`만 기록됐다(2026-11-22). 주입한 F18은 앱에도 왔기 때문에 처음 시험에서는 이 차이가 보이지 않았다. 그래서 패드에 포커스가 있는 동안 `com.apple.Carbon.TISNotifySelectedKeyboardInputSourceChanged` 분산 알림이 오면 `Lang1`을 눌렀다 뗀 것으로 보낸다(`kvm::on_input_source_change`). Caps Lock, ⌃Space, 메뉴 막대 어느 것으로 바꿔도 같다. 단, 수정 키가 있는 단축키(⌃Space)는 F18과 달리 키 자체도 앱에 온다(시험 창에서 Control, Space 누르기·떼기가 모두 기록됨). 그래서 패드는 입력 소스 단축키와 같은 키·수정 키 조합(`kvm::input_source_combos`, 패드를 열 때 읽음)의 키(Space)를 보내지 않는다. 그렇지 않으면 맞바꾸기가 켜진 상태에서 PC가 Win+Space를 받는다(사용자 확인: Win 키 메뉴가 나타남). Control은 이미 Win으로 가 있으므로, Windows 받는 쪽은 Win이나 Alt가 눌린 채 한/영·한자를 받으면 먼저 할당되지 않은 가상 키 `0xE8`을 눌렀다 뗀다(AutoHotkey의 menu mask와 같은 방법). 그러면 Win을 뗄 때 시작 메뉴가 열리지 않는다. ⌘만 눌렀다 떼서 시작 메뉴를 여는 동작은 그대로다. 패드는 그 조합(⌃Space)을 본 순간 바로 한/영을 보내고, 그 뒤 3초 안에 오는 입력 소스 변경 알림은 같은 전환으로 보고 버린다. 사용자 시험에서 Space를 먼저 떼면 정상이었지만 Control을 먼저 떼면 Win 키 메뉴가 나타났다. macOS가 Control을 뗄 때 전환을 확정하는 것으로 보이고(미확인), 그 알림으로 보낸 한/영은 Win을 뗀 뒤에 도착했다. 조합을 본 순간에는 Control(Win)이 항상 눌려 있으므로 떼는 순서와 상관없이 마스크가 적용된다. TIS API로 입력 소스를 두 번 바꾸자 알림이 정확히 두 번 왔다. Mac 자신의 입력 소스도 함께 바뀐다.
  - Windows 받는 쪽은 `Lang1`/`Lang2`를 스캔 코드가 아니라 가상 키 `VK_HANGUL`/`VK_HANJA`로 주입한다. 사용자 PC의 Caps Lock은 스캔 코드 맵으로 `0x72`가 되는데, `KBDKOR.DLL` 표에서 `0x72`는 빈 항목(`0xFF`)이다. 스캔 코드로 주입한 한/영이 IME에 닿지 않았을 가능성을 고친 것이다(미확인). 받는 쪽은 한/영·한자를 받을 때마다 로그에 남긴다(글자 키는 남기지 않는다).
  - 관찰(이 Mac mini, 2026-11-22): 입력 소스는 ABC와 2벌식 두 개다. Caps Lock을 `hidutil` `UserKeyMapping`으로 F18(HID 0x6D)로 바꿨고, 60은 F19, 61은 F18이며 둘 다 수정 키가 없다. 그래서 `lang1_keys`는 [F19, F18]이다. 맨 앞 TextEdit에 F18(`kVK_F18` 79)을 `kCGHIDEventTap`으로 주입하면 입력 소스가 바뀌었다(새 프로세스로 TIS 현재 소스를 읽어 확인). 시험용 창 앱에 F18을 주입하면 입력 소스가 바뀌면서 앱도 F18 keyDown을 받았다. 즉 Mac 패드에서 한/영을 누르면 상대로 `Lang1`이 가고 Mac 자신의 입력 소스도 바뀐다. 같은 시험에서 F18을 다시 주입했을 때 한 번은 되돌아가지 않았다(원인 미확인).
  - 미디어 키(재생, 다음 곡)는 미뤘다. Mac 보내는 쪽에서는 키 이벤트가 아니라 시스템 이벤트로 와서 패드에 오지 않을 가능성이 높고, Mac 받는 쪽은 `NX_SYSDEFINED` 이벤트를 만들어야 한다. 볼륨 키는 이미 표에 있다.
- 눌린 키 집합을 양쪽이 기억한다. 건너감이 끝나거나 링크가 끊기면 받는 쪽은 눌린 키·버튼을 모두 뗀다(아래 안전장치).

## 5. 프로토콜

### 경로

- **1단계: 기존 TCP 링크만.** 새 프레임 종류를 추가한다. 구현이 단순하고 순서가 보장된다. 단점은 Wi-Fi 패킷 손실 시 머리 막힘(head-of-line blocking): 손실 한 번에 그 뒤 이동이 20~300 ms 멈춘다. 파일 전송 중이면 이동 프레임이 파일 청크 뒤에서 기다린다. 그래서 KVM 프레임은 쓰기 큐에서 파일 데이터보다 먼저 나가야 한다(쓰기 스레드에 우선순위 큐 두 개: 제어/입력, 대량 데이터).
- **2단계: UDP 입력 경로.** 이동만 별도 UDP 소켓으로 보내고, 누적 이동량(running total)을 실어 손실을 재전송 없이 견딘다. 키·버튼은 UDP와 TCP 양쪽으로 보내고 번호로 한 번만 적용한다. 키는 TCP 링크 안에서 호스트가 만든 32바이트 난수를 `KvmLane` 프레임으로 보내 나눈다(Noise 링크 안이라 비밀이 지켜진다). 패킷은 AES-256-GCM(링크와 같은 하드웨어 경로), nonce = 송신 번호, 재전송 방지 창 64개.

### 프레임(1단계, 링크 프레임 종류 12~. 11은 `FileFrom`이 쓴다)

| 프레임 | 방향 | 내용 |
|---|---|---|
| `KvmLayout { side: u8, screens }` | 양쪽 | 이웃 방향, 화면 사각형 목록(설정 바뀔 때) |
| `KvmEnter { route: u32, y: f32, mods: u16 }` | 주는 → 받는 | 건너감 시작. 들어갈 상대 높이와 현재 수정 키 |
| `KvmMove { route: u32, mn: u32, cx: i32, cy: i32 }` | 주는 → 받는 | 건너간 뒤 누적 이동량(픽셀). 받는 쪽은 마지막으로 적용한 값과의 차이만 주입하고 `mn`이 오래된 것은 버린다 |
| `KvmButton { es: u32, button: u8, down: bool, clicks: u8 }` | 주는 → 받는 | 이벤트 번호 `es` |
| `KvmWheel { es: u32, dx: i16, dy: i16, precise: bool }` | 주는 → 받는 | 트랙패드(정밀)와 휠 노치 구분 |
| `KvmKey { es: u32, hid: u16, down: bool, mods: u16 }` | 주는 → 받는 | HID 사용 코드 |
| `KvmReturn { route: u32, y: f32 }` | 받는 → 주는 | 받는 쪽 가장자리에 닿음 |
| `KvmLeave { route: u32 }` | 주는 → 받는 | 건너감 끝(돌아옴, 취소, 안전장치). 받는 쪽은 눌린 것을 모두 뗀다 |

- 이벤트는 직전 이동의 `(mn, cx, cy)`를 함께 실어(fence) "클릭이 이동을 앞지르지 않게" 한다. TCP 1단계에서는 순서가 보장되므로 fence가 필요 없고, 2단계 UDP에서 필요하다.
- 이동 묶기: 주는 쪽은 이동을 2 ms 간격까지 모아 하나로 보낸다(최대 500 Hz). 1000 Hz 마우스도 프레임 수가 절반이다.
- 프레임 크기는 모두 20바이트 안팎이고, `SealWriter`가 큐가 빌 때 flush하므로 한 번에 하나의 Noise 메시지가 나간다. 이동 하나에 Noise 메시지 하나(헤더 2 + 태그 16 + 본문 약 20바이트).

## 6. 지연 목표

| 구간 | 목표(같은 LAN, 유선) | 측정 방법 |
|---|---|---|
| 캡처 콜백 → 큐 | < 0.2 ms | 콜백 안에서 `mach_absolute_time`/`QueryPerformanceCounter` |
| 큐 → 소켓 쓰기(암호화 포함) | < 0.3 ms | AES-GCM 20바이트 봉인은 수 µs |
| 네트워크 | 유선 0.3 ms, Wi-Fi 2~5 ms(손실 시 TCP는 수십~수백 ms) | 핑 프레임 왕복 |
| 받기 → 주입 | < 0.5 ms | 주입 직전 시각 |
| 합계(입력 → 받는 쪽 커서 이동) | 유선 < 2 ms, Wi-Fi p99 < 15 ms(2단계 UDP 이후) | 받는 쪽 로그의 시각 차(시계 동기화: 핑 왕복의 절반으로 오프셋 추정) |

- KVM 프레임은 파일 청크 뒤에서 기다리지 않아야 한다(위 우선순위 큐). 이것이 없으면 대용량 전송 중 지연이 수백 ms가 된다.
- 소켓: 입력 링크에 `TCP_NODELAY`(이미 켜져 있음). 2단계 UDP 소켓은 DSCP EF/음성 등급(`IP_TOS 0xB8`)으로 Wi-Fi WMM 음성 큐를 탄다. Windows는 `IP_TOS`를 무시하므로 qWAVE(`QOSAddSocketToFlow`, `QOSTrafficTypeVoice`)를 쓴다.

## 7. 안전장치: 입력을 반드시 돌려준다

입력을 삼키는 쪽에서 문제가 생기면 사용자가 자기 컴퓨터를 조작할 수 없게 된다. 모든 경로에서 **주는 쪽이 입력을 되찾는 것**이 기본값이다.

1. **링크 감시.** 건너간 동안 받는 쪽은 250 ms마다 `Ping`에 응답 시각을 담아 보낸다(평소 10 s보다 짧게). 주는 쪽은 500 ms 동안 아무것도 못 받으면 즉시 탭/훅의 삼키기를 멈추고 커서를 되돌린다. 링크 끊김(소켓 오류)도 같다.
2. **받는 쪽 정리.** `KvmLeave`를 받거나, 이동/이벤트 없이 링크가 끊기거나, 1 s 동안 주는 쪽 소식이 없으면 눌린 키와 버튼을 모두 뗀다(`key up`, `button up` 주입). 눌린 채 남은 Shift나 마우스 버튼이 가장 흔한 사고다.
3. **비상 탈출 키.** 주는 쪽에서 Ctrl+Alt+Shift+Esc(설정 가능)는 항상 탭/훅이 먼저 보고, 건너가 있으면 즉시 돌아온다. 이 조합은 받는 쪽으로 보내지 않는다.
4. **스레드 독립.** 캡처 콜백은 큐에 넣기만 한다. UI 스레드나 링크 쓰기가 막혀도 콜백은 바로 반환하고, 큐가 가득 차면(예: 1024개) 건너감을 끝낸다. 콜백이 늦어 OS가 탭/훅을 떼면(macOS 타임아웃 이벤트, Windows 무소식) 건너감을 끝내고 다시 건다.
5. **패닉과 종료.** 프로세스가 죽으면 OS가 탭/훅을 같이 정리하므로 입력은 돌아온다. 단 macOS의 `CGAssociateMouseAndMouseCursorPosition(false)`와 숨긴 커서는 프로세스 종료 시 복구되는지 실기기로 확인해야 한다. 패닉 훅과 `on_quit`에서 먼저 되돌린다.
6. **권한·보안 입력.** 접근성 권한이 중간에 회수되거나(macOS) 보안 데스크톱으로 바뀌면(Windows) 건너감을 끝낸다.
7. **기본 꺼짐.** KVM은 설정에서 켜야 동작하고, 켜는 순간 탈출 키를 화면에 보여 준다.

## 8. 단계

진행 상황(2026-11-21): 1단계 중 마우스(이동, 버튼, 휠)를 구현했다. 실제 프레임은 위 표와 다르다.
진행 상황(2026-11-22): 1단계 키 입력을 구현했다(`KVM` 버전 2). 아래 "키 입력" 참고.
진행 상황(2026-11-22): 3단계 키 매핑 중 수정 키 맞바꾸기, ⌘ 단축키, 한/영·한자를 구현했다(4절과 아래 3번 항목). 프로토콜은 바뀌지 않았다. 양방향 실기기 시험을 통과했다(`docs/next-tasks.md` 5번). 미디어 키는 미뤘다.
진행 상황(2026-11-22): 2단계를 시작했다(아래 "2단계 진행"). 사용자 결정: 캡처는 Mac부터(두 기기 모두 주는 쪽으로 쓴다), PC는 Mac 오른쪽이고 화면은 각 1대, 커밋 순서는 쓰기 큐 우선순위 → 링크 감시와 받는 쪽 정리 → 프로토콜 v3(건너감 시작·돌아오기) → 캡처·삼키기·탈출 키, 탈출 키는 Ctrl+Alt+Shift+Esc(Mac ⌃⌥⇧Esc) 고정, "가장자리로 건너가기"는 "원격 조작 허용"과 별개 설정이고 기본 꺼짐.

- `Hello` 끝에 KVM 버전 바이트(`wire::KVM`, 지금 1)를 덧붙였다. 양쪽 버전이 같을 때만 `Kvm*` 프레임을 보낸다. 옛 빌드는 모르는 프레임을 받으면 링크를 끊기 때문이다.
- `KvmMove { route, mn, cx, cy }`(12), `KvmButton { button, down, clicks }`(13), `KvmWheel { dx, dy }`(14, 픽셀), `KvmLeave`(15). `KvmEnter`, `KvmReturn`, 이벤트 번호 `es`는 2단계에서 넣고 그때 버전을 올린다.
- 받는 쪽은 설정 "원격 조작 허용"(기본 꺼짐)이 켜졌을 때만 주입한다. 꺼져 있으면 프레임을 버리고 눌린 버튼을 뗀다.
- 링크마다 `kvm::Injector`가 눌린 버튼을 기억하고, `KvmLeave`, 링크 끊김, 허용 꺼짐에서 모두 뗀다.
- 보내는 쪽은 Aun 창의 "원격 조작" 패드다. 이동은 점 하나에 2 px(`PAD_GAIN`)이다. 이동과 휠은 링크 큐가 차면 버리고(누적값이라 거리는 잃지 않는다), 버튼과 `KvmLeave`는 250 ms까지 자리를 기다린다.
- 키 입력: `KvmKey { hid, down }`(16). 보내는 쪽은 패드를 클릭해 포커스를 주면 rune `on_physical_input`의 물리 키(winit `KeyCode`)를 HID로 바꿔 보낸다. 받는 쪽은 HID → `KeyCode` → winit `to_scancode`로 OS 코드를 얻어 주입한다(Mac `CGEventCreateKeyboardEvent`, Windows `SendInput` 스캔 코드). 표는 `kvm::KEYS` 하나이고, winit 표에 없는 키는 OS별 `MISSING`으로 보충했다(Mac: Caps Lock, ISO §, JIS Ro, JIS 키패드 쉼표, 음소거. Windows는 없음).
  - 수정 키는 물리 위치 그대로 간다(⌘ ↔ Windows 키). Mac 받는 쪽은 눌린 수정 키를 기억해 모든 키·마우스 이벤트에 flags로 붙이고, 수정 키 자체는 `FlagsChanged`로 보낸다.
  - 받는 쪽은 눌린 키를 기억해 `KvmLeave`, 링크 끊김, 허용 꺼짐에서 마지막에 누른 것부터 뗀다. 보내는 쪽은 패드가 포커스를 잃으면 눌린 키를 뗀다. 반복은 보내는 쪽 OS의 반복을 그대로 보낸다(주입한 키는 받는 쪽 OS가 반복하지 않는다).
  - 키 입력은 `KVM` 버전 1 빌드와 섞이지 않는다. 두 기기 모두 새 빌드여야 패드가 보인다.
  - Mac 받는 쪽에서 한/영(`Lang1`/`Lang2`)은 버렸다(맥 키보드에 없는 키). 3단계에서 입력 소스 전환으로 바꿨다(4절).
- 한계(2단계에서 해결): 입력 프레임은 파일 청크 뒤에서 기다렸다. macOS는 접근성 권한이 없으면 주입한 입력을 조용히 버리므로, 허용을 켤 때 권한을 요청하고 첫 입력 때 권한 상태를 로그에 남긴다.

- 2단계 진행:
  - 쓰기 큐 두 줄(2026-11-22): 링크마다 빠른 줄(`Kvm*`, `Ping`, `FileFrom`, `FileCancel`, 64칸)과 대량 줄(파일 청크, 클립보드, 4칸)을 둔다(`node::Tx`). 쓰기 스레드는 빠른 줄만 기다리고, 대량 프레임을 넣으면 빠른 줄에 깨우기 표시(`None`)도 넣는다. 그래서 유휴 중 깨어남은 늘지 않는다. 대량 프레임 하나를 쓰기 전에 빠른 줄을 모두 쓰고, 그 사이에 쓴 빠른 프레임은 바로 flush한다. 클립보드 텍스트와 이미지는 같은 대량 줄이라 순서가 바뀌지 않는다. 한계: 이미 커널 송신 버퍼에 들어간 청크(수백 KB)는 앞지르지 못한다. 대용량 전송 중 건너가기를 실기기로 재야 한다.
  - 링크 감시와 받는 쪽 정리(7절 1·2번, 2026-11-22, `KVM` 버전 3): 입력을 보내는 쪽은 첫 입력부터 `KvmLeave`까지, 받는 쪽은 첫 입력 프레임부터 `KvmLeave`까지 쓰기 스레드가 250 ms마다 깨어나 다른 프레임이 없으면 `Ping`을 쓴다(`node::Live`, `BEAT`). 프로토콜 프레임은 그대로이고 `Ping`을 재사용한다. 읽기 스레드는 프레임마다 받은 시각을 남긴다. 보내는 쪽은 500 ms(첫 입력 시각부터도 셈) 동안 아무것도 못 받으면 `Note::InputLost`를 한 번 알리고, 받는 쪽은 1 s 동안 못 받으면 눌린 키와 버튼을 뗀다. 판정은 링크마다 두는 감시 스레드(`node::watch`)가 한다. 입력이 오가는 동안만 250 ms마다 깨어나고, 평소에는 잠들어 있어 유휴 중 깨어남이 늘지 않는다. 읽기 스레드는 `read_frame`에서 막혀 있고(읽기 시간 제한을 짧게 하면 프레임 중간에서 끊긴다), 쓰기 스레드는 링크가 멈추면 파일 청크를 쓰다가 막히기 때문이다. 처음에는 쓰기 스레드에서 판정했는데, 양쪽으로 큰 파일이 가는 중에 링크를 멈추자 5 s 안에 알림도 정리도 오지 않았다(테스트로 재현한 뒤 고침). 지금 앱은 `InputLost`를 받으면 그 기기의 패드를 닫고 "상대가 응답하지 않아 원격 조작을 멈췄어요"를 보인다. 캡처가 생기면 같은 알림에서 삼키기를 멈춘다. 옛 빌드(버전 2)는 250 ms마다 쓰지 않아 끊긴 것으로 보이므로 버전을 올렸다. 시험: 중계 소켓을 멈춰 링크를 닫지 않고 조용하게 만들면 알림이 0.5 s, 정리가 약 1.0 s 뒤에 온다. 1 GB 파일이 양쪽으로 가는 중에 멈춰도 같다(`tests/link.rs`).
  - 건너감 시작·돌아오기 프레임(2026-11-22, `KVM` 버전 3에 포함, 아직 배포한 적 없는 버전이라 올리지 않음): `KvmEnter { route, side, at }`(17)과 `KvmReturn { route, at }`(18). 5절 표와 다르다: 상대 높이 `f32` 대신 가장자리를 따라간 위치 `at`(0~65535)이고, `side`는 받는 쪽 화면에서 주는 쪽이 있는 가장자리(0 왼쪽, 1 오른쪽, 2 위, 3 아래)다. 그래서 받는 쪽은 배치 설정이 없어도 된다(`KvmLayout`은 넣지 않음). 받는 쪽은 `KvmEnter`에서 포인터를 그 가장자리의 픽셀 위에 놓고(`kvm::entry`), 이동이 그 가장자리 밖으로 밀면(`kvm::past`, 1 px만 밀어도) `KvmReturn`을 한 번 보낸다. 주는 쪽 노드는 `Note::Returned`로 알린다. 패드는 `KvmEnter`를 보내지 않으므로 돌아오기가 없다. 화면은 모든 화면을 감싼 상자로 본다(사용자는 기기마다 화면 1대). 이동량은 받는 쪽 포인터의 픽셀이고, Mac은 포인트 단위다.
  - 캡처의 순수 부분(2026-11-22): 탈출 키 판정 `kvm::escape`(Ctrl·Alt·Shift가 왼쪽이든 오른쪽이든 눌린 채 Esc, ⌘는 상관없음), Mac 키 코드 → HID `kvm::hid_of`, `flagsChanged`를 수정 키 누르기·떼기로 바꾸는 `kvm::mac_modifier`(왼쪽·오른쪽 장치 비트로 판정: 두 Shift 중 하나만 떼도 Shift 플래그는 남는다), 캡처한 입력을 프레임으로 바꾸는 `kvm::Driver`(건너갈 때마다 새 route, 그 안에서 누적 이동량). 설정 `cross`(기본 꺼짐)와 `side`(상대 화면 방향, 0 왼쪽·1 오른쪽, 기본 오른쪽). `hid_of` 왕복 시험에서 winit 표의 Mac 볼륨 키가 Apple `Events.h`보다 하나씩 밀려 있는 것을 찾았다(winit: 올리기 0x49, 내리기 0x4A. Apple: 0x48, 0x49, 음소거 0x4A). 그래서 Mac 받는 쪽은 볼륨 내리기를 음소거로 주입하고 있었다. Aun의 보충 표가 winit보다 먼저 쓰이도록 바꿨다(실기기 미확인).
  - Mac 캡처(2026-11-22, `capture.rs`, 실기기 미시험): 설정 "가장자리로 건너가기"(기본 꺼짐)와 "상대 화면: 오른쪽/왼쪽"은 Mac에서만 보인다. 켜면 입력 모니터링 권한을 확인·요청하고(`CGPreflightListenEventAccess`/`CGRequestListenEventAccess`), 세션 이벤트 탭(`kCGEventTapOptionDefault`)을 전용 스레드의 런루프에 건다. 탭을 만들지 못하면 설정을 끄고 권한 안내를 보인다. 켤 때 "반대로 밀거나 ⌃⌥⇧Esc"를 화면에 보인다.
    - 건너감: 수정 키와 버튼이 모두 떼어진 일반 이동(`MOVED`)만 건너감을 시작한다. 눌린 채 건너가면 Mac 앱이 누르기만 받고 떼기는 상대로 가기 때문이다. 이동이 상대 쪽 가장자리 밖으로 밀면(`kvm::past`, 화면 상자는 캐시하고 밖으로 보일 때 다시 읽음) `CGAssociateMouseAndMouseCursorPosition(false)`로 커서를 떼고 그때부터 모든 마우스·키 이벤트를 삼킨다(콜백이 NULL 반환). 이동량은 `kCGMouseEventDeltaX/Y`, 스크롤은 픽셀 값(`PointDeltaAxis1/2`), 키는 `kvm::hid_of`, 수정 키는 `kvm::mac_modifier`, Caps Lock은 토글마다 누르기·떼기 한 번.
    - 콜백은 원자 변수와 `try_send`만 쓴다(잠금·로그 없음). 보내는 스레드(`aun-cross`)가 `kvm::Driver`로 프레임을 만들고 ⌘·Ctrl 맞바꾸기 설정을 키에 적용해 `send_input`으로 보낸다. 건너간 동안만 50 ms마다 깨어난다.
    - 끝내기(`State::end`, 어느 스레드에서든, 여러 번 불러도 한 번만): 커서를 가장자리로 옮기고(`CGWarpMouseCursorPosition`) 다시 붙인 뒤, 보내는 스레드가 `KvmLeave`를 보낸다. 끝나는 경우: `KvmReturn`(route가 맞을 때, 그 위치로), ⌃⌥⇧Esc(상대로 보내지 않음), 큐 1024개가 참, 탭이 타임아웃·사용자 입력으로 꺼짐(다시 켬), `Note::InputLost`, 상대 링크가 없어짐(`refresh`), 설정 끄기·방향 바꾸기, 앱 종료와 패닉(`release_cursor`). `KvmReturn`이 아닌 이유로 끝나면 포인터가 가장자리에서 50 px 멀어져야 다시 건너간다(멈춘 링크로 다시 들어가지 않게).

Mac 입력 소스도 바뀌지 않은 것으로 보아 탭이 F18을 받아 삼키고 PC에 F18로 보낸 것이다(추론). 패드가 쓰는 단축키 목록(`input_source_combos`)은 앱에 오지 않는 수정 키 없는 단축키를 빼기 때문이다. 고침: 탭은 탭을 켤 때 읽은 모든 입력 소스 단축키(`kvm::input_source_keys`, 이 Mac은 [F19, F18], 수정 키 없음)와 같은 키·수정 키를 `Lang1` 누르기·떼기로 보낸다. 삼키므로 건너간 동안 Mac 자신의 입력 소스는 바뀌지 않는다(실기기 미시험).
    - 한계: 커서를 숨기지 않는다(`CGDisplayHideCursor`는 배경 앱에서 확실하지 않고, 숨기기·보이기 횟수가 어긋나면 더 나쁘다). 건너간 동안 Mac 커서는 가장자리에 보인 채 멈춰 있다. 건너가 있지 않을 때도 키 이벤트가 탭을 지나간다(콜백은 바로 반환). 이동을 2 ms씩 묶지 않는다. 보안 입력(7절 6번), 화면 구성 변경 콜백, Windows 캡처는 아직 없다. 입력 소스 단축키(이 Mac은 F18이 된 Caps Lock)가 건너간 동안 탭보다 먼저 시스템에 가는지는 미확인이다.
    - 실기기 시험 항목: 오른쪽 가장자리로 건너가 PC를 움직이기·클릭·끌기·스크롤·입력, PC 왼쪽 가장자리로 밀어 돌아오기(같은 높이로 돌아오는지), ⌃⌥⇧Esc로 돌아오기(맞바꾸기 켬, PC에 시작 메뉴가 열리지 않는지, PC에 키가 남지 않는지), 건너간 동안 PC Wi-Fi 끄기(Mac이 0.5 s 안에 돌아오는지), 양쪽으로 큰 파일을 보내는 중 건너가기(지연, 잘못된 돌아옴), Shift나 버튼을 누른 채 가장자리로 밀기(건너가지 않아야 함), Windows 패드로 Mac 포인터를 오른쪽 가장자리 밖으로 밀기(건너가지 않아야 함), PC에서 원격 조작 허용을 끈 채 건너가기(0.5 s 뒤 돌아오고 안내가 보여야 함), PC에서 작업 관리자를 앞에 둔 채 건너가기(바로 돌아오고 안내가 보여야 함), Mac에서 다른 앱을 앞에 둔 채 건너가기(Mac 커서가 움직이지 않아야 함), 건너간 동안 Aun 강제 종료(커서가 마우스에 다시 붙는지), 건너간 동안 Caps Lock(한/영).

1. **받는 쪽 주입만**(위험 낮음): 상대가 보낸 이동/클릭/키를 주입. 테스트용으로 Aun 창 안의 "원격 트랙패드" 영역에서 드래그하면 상대 커서가 움직이게 한다. 입력을 삼키지 않으므로 안전하게 지연과 키 매핑을 실기기에서 맞춘다.
2. **가장자리 건너감, TCP 1단계**: 캡처, 삼키기, 안전장치 1~5. 쓰기 큐 우선순위.
3. **키 매핑 다듬기**: 한/영, 수정 키 옵션, 미디어 키. 패드에 포커스가 있을 때 Mac의 ⌘ 단축키(특히 ⌘Q, 지금은 상대에게 가면서 Aun도 종료한다)를 상대로 보낼지 여기서 함께 정한다(2026-11-22 사용자 결정).
   - ⌘ 단축키(2026-11-22 사용자 결정, 구현): 패드에 포커스가 있고 이 키보드의 ⌘가 눌린 동안 Mac Aun은 메뉴 막대(`NSApp.mainMenu`)를 떼어 둔다. 그래서 ⌘Q·⌘W·⌘H·⌘M 같은 메뉴 단축키가 Aun에서 실행되지 않고 상대에게만 간다. ⌘를 떼거나, 패드가 포커스를 잃거나, 패드가 닫히면 메뉴를 되돌린다. ⌘를 누르고 있는 동안 메뉴 막대가 비어 보인다. ⌘Tab·⌘Space처럼 시스템이 먼저 가져가는 조합은 패드에 오지 않는다(2단계 이벤트 탭에서만 가능).
4. **UDP 입력 경로**(2단계): 누적 이동량, 번호 붙인 이벤트, 재전송 방지, DSCP.
5. **여러 모니터 배치 편집 화면**.

## 9. 테스트

- 단위: HID ↔ macOS 키 코드 / Windows 스캔 코드 표 왕복(모든 키), 가장자리 판정(화면 합집합, 안쪽 경계 무시), 누적 이동량 적용(중복·순서 바뀜·손실), 이벤트 번호 중복 제거.
- 통합(루프백, 주입은 가짜 싱크): 두 노드 사이 건너감 → 이동 → 클릭 → 돌아옴, 링크를 끊었을 때 받는 쪽이 눌린 키를 모두 떼는지, 주는 쪽이 500 ms 안에 돌아오는지.
- 실기기만 가능한 것: 실제 탭/훅, 권한 흐름, 보안 입력, 잠자기/깨우기 중 건너가 있던 경우, 입력기 전환, 지연 측정.
